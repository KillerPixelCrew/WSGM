This file is the single authoritative answer for every blocking `P0` decision. Where the design
documents already determine an answer, that answer is recorded here in decision form and the source
is cited. Where they contradict each other, the contradiction is named and one answer wins.

Each entry has one of three states:

- **Resolved** — the design documents already determine it; this record only makes it operative.
- **Decided** — not previously determined; decided here, with the rejected alternative named.
- **Open, scheduled** — not a decision but an audit, owned by a named later phase.

A decision recorded here supersedes any conflicting prose in the four design documents. Conflicts
found while writing this record are listed in [Document corrections](#document-corrections) and must
be applied to the source documents in the same change that consumes them.

## P0.1 Cross-document behavior and sequencing

### P0-001 · Controller activation transaction — **Resolved**

Source: `claw-8-a2vm-plugin.md` "HidHide transaction" and "Activation order".

The physical device is hidden **before** the virtual target is created. The ordered transaction is:

| Step | Action                                                             | Owner |
| ---- | ------------------------------------------------------------------ | ----- |
| A1   | Add DeviceHost to the HidHide allowlist                            | WSGM  |
| A2   | Add WSGM-owned HidHide hide entries for the exact physical devices | WSGM  |
| A3   | Verify DeviceHost can still read the now-hidden physical source    | WSGM  |
| A4   | Create the selected HIDMaestro virtual target                      | WSGM  |
| A5   | Verify the virtual target enumerated and is readable               | WSGM  |
| A6   | Enable normal canonical-to-target routing                          | WSGM  |

Rollback is strict reverse order and removes only WSGM-owned state: A6→A1. Failure at A3 removes A2
then A1 and reports `hidhide-readback-failed`; failure at A4/A5 removes the partial target, then A2,
then A1. Every intermediate state is recorded in the recovery journal before the step that creates
it, so a process death between any two steps is reconcilable at next start (`P4.8`).

Rejected alternative: create the target first, then hide. It guarantees a window in which the game
sees both the physical controller and the virtual target — duplicate input, unstable XInput slot
assignment, and ambiguous binding, which `2.0-design.md` names as the reason only one virtual target
may be active. The chosen order's failure mode (briefly no controller, deterministic rollback) is
strictly better than duplicate input, and `INV-019`'s fail-open-to-usable-input rule is satisfied by
the rollback restoring the physical device.

### P0-002 · HidHide requirement — **Decided**

HidHide is **mandatory whenever WSGM controller management is active**. It is not a user-facing
on/off setting.

- Controller management on ⇒ WSGM-owned HidHide entries exist for the plugin's physical controller
  identities, and DeviceHost is allowlisted.
- HidHide absent, unhealthy, or its transaction failing ⇒ controller management cannot activate.
  This is a degraded state with the structured reason `prerequisite-missing`, not a fault: Device
  Integration continues, all non-controller capabilities stay active, and UI/game input falls back
  to the existing SDL + Steam Input lease path.
- Controller management off ⇒ HidHide is untouched, per `2.0-design.md`.

Rejected alternative: a configurable "hide physical controller" toggle.
`Controller management on + physical device visible` is the same duplicate-input state `P0-001`
exists to prevent, and the whole managed-UI-input design depends on the physical device being
readable by DeviceHost while invisible to Steam. Making it configurable creates a second invalid
configuration next to `INV-002`'s.

### P0-003 · Provisional capability surface versus the Phase 4 overlay redesign — **Decided**

Two surfaces are separated explicitly:

**Provisional (ships during `P4.9`, removed in `P9`):** one temporary `Device` page hosted inside
the _existing_ overlay window, reachable from the existing Tools navigation. It contains only a
generic capability-driven renderer (toggle, range, choice, action, read-only value), the device
identity/health header, and the diagnostics list. It has no bespoke per-capability layout, no
profile editor, no fan-curve editor, and no glyph preview.

**Final (`P9`):** the complete `Device` destination in the new navigation shell.

What is removed at `P9`: the temporary page host, its Tools entry, and any layout code written for
it. What survives: the capability view models, the generic control renderers, the semantic
display-schema resolution, and the diagnostics projection — these are written once, against the
frozen `P1` contracts, and reused by the final destination.

Consequence for the backlog: `P4.9` may not grow bespoke device UI. Anything that cannot be
expressed by the generic renderer waits for `P9`.

### P0-004 · OEM sources and actions surviving with controller management off — **Resolved**

Source: `claw-8-a2vm-plugin.md` — "External controller management does not automatically disable the
plugin-owned OEM event path or WSGM's QAM mapping", and the OEM control table.

| Logical control           | Physical source                | Survives controller management off |
| ------------------------- | ------------------------------ | ---------------------------------- |
| OEM1 (Claw, short)        | MSI WMI event `0x29`           | Yes                                |
| OEM2 (Quick Settings)     | MSI WMI event `0x58` / `0x2A`  | Yes                                |
| Firmware chord suppressor | `WH_KEYBOARD_LL`, plugin-owned | Yes                                |
| OEM3 / M1                 | Raw HID byte 7 bit 4           | **No**                             |
| OEM4 / M2                 | Raw HID byte 7 bit 3           | **No**                             |

M1/M2 are only observable while the plugin holds DirectInput-mode acquisition. Releasing that
acquisition restores the captured controller mode — on the reference unit, XInput — where the rear
paddles are not exposed at all. With controller management off, M1/M2 assignments therefore become
unavailable with the structured reason `resource-released`, their configured values are **retained**
in configuration, and they reactivate unchanged when controller management is turned back on.

The generalized rule for every device: an OEM source survives controller-management-off if and only
if it does not depend on the plugin's physical-controller resource. Plugins declare that dependency
per logical control; WSGM does not infer it.

### P0-005 · Physical handheld profile and presentation authority — **Resolved / Decided**

Source: `controller-glyph-integration.md` — "Disabling only virtual-controller management does not
remove the physical-device glyph profile" and "verify WSGM does not mislabel it as the active
handheld".

**Resolved:** the glyph profile belongs to Device Integration, not controller management. Turning
controller management off leaves the profile, the Steam glyph patch, and the WSGM glyph service
untouched. Turning Device Integration off removes them.

**Decided — presentation authority:**

| Surface                                       | Presentation identity                                                                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| WSGM navigation hints, input test             | The **active UI input source**: managed canonical ⇒ handheld profile; SDL fallback ⇒ generic glyphs derived from the SDL controller type |
| WSGM Device pages describing the handheld     | Always the handheld profile while Device Integration is on                                                                               |
| Steam Input route about a specific controller | The handheld profile only when that route's subject controller is the handheld                                                           |
| Steam Input route with no resolvable subject  | Native Steam glyphs (fail-open)                                                                                                          |

An external or unmanaged controller is never labelled with the handheld profile. When the Steam
route's subject cannot be determined from the DOM, the patch does not apply — `P8.6` owns proving
whether the subject is resolvable, and a negative result narrows the patch to device-level diagram
tiers rather than expanding it.

### P0-006 · Win+G suppressor and elevated foreground — **Resolved**

Source: `claw-8-a2vm-plugin.md`, `[HW 2026-08-27]` process-boundary note.

The reviewed Claw package is spawned elevated (it inherits WSGM's existing elevation, see
`INV-008`), so its `WH_KEYBOARD_LL` hook is installed from an elevated process and is not outranked
by an elevated foreground window. **No fixed-operation helper is approved and the release claim is
not narrowed.** `P0-006` becomes ordinary validation work in `P5.4`: prove the elevated-host hook
over an elevated foreground window on hardware.

Remaining stated limits, unchanged and not part of the claim: the secure desktop is not intercepted;
Windows may silently remove a timed-out low-level hook, so re-arm on every known lifecycle
transition; all hook state resets on desktop/session change.

### P0-007 · Authoring, review, and installation of new mutation trials — **Decided**

Mutation trials are **repository artifacts, not installable content.** There is no mechanism for a
user or third party to add a trial to a shipped Device Lab.

1. **Propose** — a trial is a source change in `catalog/trials/` with its metadata (exact identity
   and firmware gates, endpoint, maximum writes, effect, lease, rollback, emergency action, timeout,
   retry, cooldown, expected observation) and its own fixtures.
2. **Review** — maintainer review against the `P2.7` safety checklist. A trial that combines
   capabilities, lacks an independent observation, or lacks a verified restore path is refused.
3. **Pin** — the build computes the trial's content hash and writes it into the catalog manifest;
   the manifest ships inside the Device Lab package. `probe run` resolves a trial ID to that pinned
   hash and refuses any mismatch.
4. **Promote** — a trial's _results_ promote a claim through `Corroborated → HardwareVerified`; the
   trial itself is never "promoted", it is either in the reviewed catalog or it does not exist.

Developer-authored trials execute only from a **source build** of Device Lab in Developer Mode,
under a distinct command (`probe run --developer <path>`), which is unavailable in any shipped
package. This keeps `P2-061`/`P2-062` literally true for every user-reachable build.

Rejected alternative: signed third-party trial packages. That would make hardware-mutation authority
a distribution problem, which `device-plugin-system-and-tooling.md` explicitly refuses ("imported
captures, recipes, manifests, plugins, or evidence locks can never authorize a hardware mutation").

### P0-008 · Native QAM first-milestone scope — **Decided**

The scope rule, frozen now, is: **a QAM control is interactive only if WSGM already owns a frozen
semantic command contract for it. Everything else is a read-only projection or is deferred.**

Applied to the first native-QAM milestone (`P7.6`):

| Native QAM element         | First milestone                                                                                            |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| TDP slider + current value | **Interactive** — `power.primary-limit` capability                                                         |
| Frame limiter              | **Interactive** — RTSS service                                                                             |
| Performance-overlay level  | **Interactive** — RTSS service                                                                             |
| Controller target          | **Interactive** — WSGM controller adapter                                                                  |
| Performance profile        | **Deferred** — depends on the per-application profile semantics frozen in `P4.5`; revisit after that lands |
| Performance data           | **Read-only projection**, and only if live probing finds a healthy native component; otherwise deferred    |

Performance data stays read-only in the first milestone because it is the only high-rate path in the
QAM and `claw-8-a2vm-plugin.md`'s performance budget bounds telemetry to a low rate that stops when
no surface consumes it. A read-only projection needs no command contract and can be dropped without
a compatibility break if probing shows the native component is gone.

### P0-009 · RTSS controls with Device Integration off — **Decided**

RTSS frame limit and performance-overlay level **remain fully available with Device Integration
off.** They are Windows-application controls with no plugin dependency; gating them on Device
Integration would violate `INV-001`.

Ownership: one WSGM-owned `PerformanceService` is the single implementation. It is projected into:

- **Device › Power and thermals** when Device Integration is on, adjacent to TDP.
- **System › Performance** when Device Integration is off.
- **Native Steam QAM**, independent of Device Integration.

There is exactly one service instance, one state, and one command path; the two overlay locations
are projections of it and never both visible at once.

Rejected alternative: a permanent home under `System` regardless of Device Integration. It reads
more cleanly in the navigation but separates frame limit from TDP, which are adjusted together
during play — and the QAM already colocates them.

### P0-010 · Selected-plugin cardinality and tie-breaking — **Decided**

**Exactly one logical handheld and one selected plugin package per machine for 2.0.** Device
identity is rooted in SMBIOS, so the machine _is_ the handheld; multiple simultaneous handhelds are
not a supported configuration. Detachable endpoints (controller halves, sensors) belong to that one
logical device's resource graph and never nominate a second package.

When more than one installed package's hard identity gates all match, selection applies these keys
in order and stops at the first that discriminates:

1. Trust tier: `WSGM-reviewed` > `Signed external` > `Sideloaded community` > `Developer`.
2. Device-definition specificity: the count of exact (non-weighted, non-optional) identity
   predicates satisfied.
3. Package version, descending.
4. Package ID, ordinal ascending — a deterministic final tie-break so selection never depends on
   enumeration order.

If two candidates are equal on all four keys, selection **fails closed**: no package is selected,
Device Integration reports `ambiguous-package-selection`, and the Device page requires an explicit
user choice, which is then persisted under the device identity and wins over keys 1–4 until the user
changes it or the chosen package is uninstalled.

A stale device (removed, not re-enumerated) does not change selection; it invalidates the device
generation and marks affected capability state `Stale` per `P1-021`.

### P0-011 · Descriptor replacement and consumer invalidation — **Decided**

Capability descriptors are immutable values carried in a versioned set with a monotonic **descriptor
generation** per device generation. AC/DC state is _not_ a descriptor change: AC and DC availability
are immutable descriptor fields, and the live AC/DC condition is reported in the capability _state_
message as availability plus a structured reason.

A descriptor generation is incremented, and a complete replacement set is published, when any of the
following change: controller/EC/BIOS/MCU firmware version, the endpoint set or an endpoint's report
shape, dependency health that adds or removes a capability, or the plugin/module version after a
package update.

On a new descriptor generation, WSGM:

1. Discards every cached descriptor for that device generation.
2. Completes in-flight commands as `Indeterminate` — never as `Rejected`, because the outcome is
   genuinely unknown.
3. Re-projects desired state against the new descriptors. A persisted desired value now outside the
   published range is **not silently clamped**; it is retained, reported as
   `desired-value-out-of-range`, and requires an explicit user action to adopt the nearest legal
   value.
4. Re-renders capability UI from the new set; a capability absent from the new set disappears rather
   than lingering as unavailable.

### P0-012 · Desired-state precedence and captured hardware state — **Decided**

**Captured hardware state is restoration-only.** It is written to the recovery journal at
acquisition, used exclusively to restore on release or reconcile after a crash, and never
participates in desired-state resolution. WSGM never adopts an observed hardware value as a desired
value.

Desired-state layers, lowest precedence first:

| #   | Layer                     | Scope                               | Persistence |
| --- | ------------------------- | ----------------------------------- | ----------- |
| 1   | Global default            | Per capability, per device identity | Persistent  |
| 2   | AC/DC policy              | Per capability, per power state     | Persistent  |
| 3   | Selected hardware profile | Named user profile                  | Persistent  |
| 4   | Per-application override  | Matched running application         | Persistent  |
| 5   | Temporary request         | Current session                     | Volatile    |

The effective desired value is the highest layer that has a value for that capability. Layer 5 is
dropped on: profile change, per-application match change, device generation change, Device
Integration off, and WSGM exit. It survives suspend/resume and Desktop/Game Mode transitions.

An overlay or QAM edit writes to the **highest currently-active persistent layer** (4 if an
application override is active, else 3 if a profile is selected, else 2 if an AC/DC policy exists
for the current power state, else 1). The editing surface names the layer it is writing. A
session-only change is a separate, explicit action that writes layer 5.

### P0-013 · Full-deactivation timeout topology — **Decided**

Deactivation is four sequential phases, each with its own budget. A phase that times out is recorded
and **the sequence continues** — a phase timeout never aborts the remaining phases, because the
later phases remove WSGM-owned state that would otherwise strand the user.

| Phase | Work                                                                                                   | Budget |
| ----- | ------------------------------------------------------------------------------------------------------ | -----: |
| A     | WSGM: stop accepting commands, establish input fallback, neutralize the virtual target (HidHide stays) |    1 s |
| B     | Plugin: stop readers, release physical acquisition, restore controller mode, await re-enumeration      |    6 s |
| C     | Plugin: restore fans/scenario/lighting/other snapshots, close transports, finalize journal             |    6 s |
| D     | WSGM: remove the virtual target, remove only WSGM-owned HidHide entries, dispose the host              |    2 s |

Total nominal budget 15 s for the Settings master toggle. There are **no retries inside
deactivation** beyond each individual step's own bounded retry; the budget is not extended.

On any phase timeout: mark exactly the affected resource `restore-unverified`, write its
recovery-journal entry before proceeding, continue to the next phase, and force host termination at
the end of phase D. WSGM then shows a persistent warning state on the Device page and reconciles at
next start (`P4.8`), which is the only place a restoration is retried. WSGM never reports an
unverified handoff as clean restoration.

### P0-014 · Plugin update, removal, and deferral during an active device cycle — **Decided**

Source constraint: "Plugin runtime removal, update, or replacement is not an additional lifecycle
trigger while Device Integration is active."

- **Update:** downloaded, verified, and **staged**. It applies at the next device-cycle start — next
  WSGM start, or the next Device Integration off→on. The Device › Overview page shows "Update staged
  — applies on next start" with the version and change summary.
- **Apply now:** an explicit user action that runs the full `P0-013` deactivation, swaps the
  package, and reactivates. It is presented as exactly that, with the interruption stated. WSGM
  never performs this implicitly.
- **Remove:** refused while the device cycle is active. The Device page offers "Turn Device
  Integration off and remove", which runs full deactivation first and leaves Device Integration off.
- **Defer:** a staged update may be dismissed; it stays staged and is re-offered at the next start.
  Dismissal never deletes the verified package.

A staged update is discarded and re-fetched if its signature, hash, or publisher verification fails
at apply time.

### P0-015 · Quarantine behavior — **Decided**

Quarantine triggers when DeviceHost exits unexpectedly **3 times within 5 minutes**. Restart backoff
before quarantine is 1 s, 4 s, 16 s.

On quarantine:

- **Desired state is retained**, at every layer. Quarantine is a fault, not a user intent change.
- **Input fails open:** the virtual target and every WSGM-owned HidHide entry are removed, so the
  physical controller is visible again; UI and game input revert to SDL + Steam Input lease. Leaving
  a device hidden with no host to read it would strand the user's only controller.
- The Device page shows `Quarantined` with the fault reason, the exit code, and the last
  recovery-journal entry, plus any resource left `restore-unverified`.
- **Manual retry only.** A "Retry now" action is available with a 60 s cooldown between attempts.
  Automatic restart never resumes on its own.
- Quarantine clears on: a successful activation, Device Integration toggled off→on, WSGM restart, or
  a staged package update being applied.

Quarantine is per **package/host**, not per resource. A single resource fault is handled by
per-resource degradation (`P1-026`) and never quarantines the host.

### P0-016 · Controller-target matching and precedence — **Decided**

- **Identity:** the application identity WSGM already uses for per-game settings and launch fixes —
  Steam AppID when known, otherwise the normalized executable path plus file identity. No new
  identity scheme is introduced.
- **Precedence:** per-application override > global default. An unknown application uses the global
  default; it never inherits the previous application's target.
- **When a switch occurs:** at application start, and at application exit back to the global
  default. Never mid-session for a running application.
- **Debounce and safety:** a switch is deferred while a WSGM UI capture is active and applied on
  capture release; a switch is skipped (and logged) if the previous switch completed less than 2 s
  ago. Target replacement always removes the current target before creating the next.
- **User-visible consequence:** WSGM surfaces that an already-running application may need to be
  restarted to bind the replacement target, per `2.0-design.md`.

### P0-017 · Glyph selection precedence and persistence — **Resolved**

Source: `controller-glyph-integration.md` "Selection and controls".

Setting values: `Automatic` (default), `Native Steam glyphs`, or a manual reviewed catalog profile.

Precedence: an explicit user selection (`Native Steam glyphs` or a manual profile) always wins.
`Automatic` resolves to the exact verified profile advertised by the active device definition, and
falls back to native Steam glyphs when there is no exact verified profile. WSGM never guesses a
visually similar handheld.

Persistence: stored under the WSGM device identity, survives WSGM and Steam restarts, and is not
reset by a plugin update. A manual profile ID that no longer resolves in the catalog falls back to
`Automatic` and reports `glyph-profile-missing`. The selection is device-scoped, never
per-application.

### P0-018 · Threshold for declaring a Valve component removed — **Decided**

A WSGM-rendered replacement may only be authorized for a component that satisfies **all four**:

1. The module, route, store, or component is absent from the current Steam build under its known
   fingerprint **and** under structural discovery (renamed/rehashed variants), not merely unmatched
   by one selector.
2. It is absent across **at least two consecutive Steam stable builds spanning at least 30 days**.
3. A deterministic `absent` probe exists in the patch registry and is covered by a fixture, so the
   claim is re-testable after every Steam update.
4. Explicit maintainer sign-off is recorded in the patch entry, naming the builds inspected.

Anything short of all four means the patch is marked incompatible and falls back to native rendering
or a no-op. A failing selector is never evidence of removal.

### P0-019 · Audited plugin dependency lifecycle — **Decided**

Two dependency kinds, never conflated:

- **`oem-installed`** — present on the target system from the factory or installed by the user (the
  MSI WMI provider is the reference case, see `P0-040`). WSGM never installs, repairs, registers, or
  redistributes these. Absence makes the dependent capability unavailable with
  `prerequisite-missing`.
- **`wsgm-audited`** — entries in WSGM's audited component catalog (HidHide, HIDMaestro, usbip-win2
  and similar), each pinned by version, hash, signer, license, install location, ACL, health check,
  upgrade path, rollback, and removal behavior.

Only the WSGM installer/updater — never DeviceHost, never a plugin — installs, repairs, upgrades, or
removes a `wsgm-audited` component. Installation is opt-in: the Device page reports the missing
component and offers an action that hands off to the installer path. Health checks run at activation
and on demand from Device diagnostics. Removal is offered in Settings and is never required to
disable a feature. A plugin declares dependencies and reports their observed health; it has no
install authority of any kind, and its manifest cannot add an entry to the audited catalog.

### P0-020 · Release fallback if HIDMaestro misses a mandatory gate — **Decided**

**Ship Device Integration without controller management.**

Device Integration's value — power, fans, lighting, telemetry, OEM buttons, native QAM, glyphs — is
independent of virtual-controller emulation, and `INV-002` already makes controller management an
optional child. If HIDMaestro fails an acceptance gate in `P6.11`, controller management is held
back as a post-2.0 feature; the setting is hidden rather than shown as broken, and every unmanaged
path (SDL + Steam Input lease) is the shipping behavior.

Delaying the whole release is rejected: it makes one optional subsystem block four completed ones.
Revisiting the backend decision (VIIPER or another target) is a separate evaluation, not a release
gate.

### P0-021 · First WSGM 2.0 release boundary — **Decided 2026-08-27**

2.0 is a **platform release**, not a single-device release. It ships:

- Device plugin platform, DeviceHost, semantic capability router, profiles, recovery journal.
- MSI Claw A2VM plugin: lifecycle/OEM safety (M1), power and thermals (M2), controller/rumble/motion
  (M3), lighting (M4).
- Controller management with Steam Deck Composite, Xbox 360, and DualShock 4.
- Native QAM restoration at the `P0-008` first-milestone scope, plus RTSS.
- Handheld glyph patch and catalog.
- Final overlay information architecture.
- Device Lab `D0`–`D4`.
- **`D5` in full:** the public contributor workflow, third-party package trust tiers, publisher
  signing/revocation, package validation, and the plugin submission and retail-promotion process.

Explicitly later: DualSense target; optional Claw capabilities (charge limit, scenario extras, M1/M2
profile repair).

Consequences, because `D5` is now in scope rather than deferred:

- `P0-042`, `P0-043`, and `P0-045` become shipping contracts rather than forward-looking policy.
  Every tier in `P0-042` must be reachable by a real user on a real install, and the
  signed-external/sideloaded/developer paths need the same test coverage as the reviewed path.
- `P2.11` and `P2.12` are release gates for 2.0, not follow-up work.
- `P10.9` must publish contributor templates, the submission workflow, and the hardware-evidence
  requirements, not just internal documentation.
- The de-elevated spawn path for untrusted packages (`INV-008`) becomes a shipping code path that
  needs its own acceptance matrix — an untrusted package must lose exactly the privilege-dependent
  capabilities and nothing else.

Dependent backlog: `P2.11`, `P2.12`, `P5.12`, `P6.3`, `P10.9`, `P10.10`.

| Field or action                                                      | Owner              |
| -------------------------------------------------------------------- | ------------------ |

| Descriptors, report descriptors, endpoint graph, `bcdDevice`         | Device diagnostics |
| Plugin package, module versions, evidence lock IDs, trust tier       | Device diagnostics |
| Per-capability state, quality, observation time, structured reason   | Device diagnostics |
| Last N hardware transactions and their outcomes                      | Device diagnostics |
| Recovery-journal status and unverified restorations                  | Device diagnostics |
| Resource ownership and detected conflicts                            | Device diagnostics |
| DeviceHost generation, restart count, quarantine state               | Device diagnostics |
| HidHide owned entries, virtual target state, input-arbiter source    | Device diagnostics |
| Glyph profile, patch health, selector fingerprint, theme conflict    | Device diagnostics |
| Per-component CPU, sample rate, queue depth, dropped events          | Device diagnostics |
| Export sanitized device trace                                        | Device diagnostics |
| Log level and verbosity                                              | WSGM diagnostics   |
| Log file location and "open log"                                     | WSGM diagnostics   |
| WSGM version, update channel, update state                           | WSGM diagnostics   |

Device diagnostics live in the overlay (`Device › Diagnostics`) per `INV-010`; WSGM diagnostics live
in Settings. The general bundle embeds a device **summary** — identity gate result, capability
health counts, last fault, unverified restorations — but never raw device streams. Both exports use
the same sanitizer.

Front OEM buttons may **not** be mapped to a virtual-target button. Doing so would turn a front OEM
control into gameplay input, which is exactly the general remapper `INV-013` forbids; the
rear-paddle exception exists because rear paddles already _are_ gameplay controls on the richest
target.

On a target with no rear controls, `VirtualTargetRearButtonN` is unavailable with
`unsupported-by-target`; the rear control may then take any WSGM action or `Disabled`. Routing stays
mutually exclusive per press — forwarded as a rear control **or** consumed as a WSGM action, never
both.

`CycleControllerTarget` is deliberately excluded: a target switch causes device re-enumeration and
may require an application restart, which is not acceptable as an accidental button press.

### P0-024 · Make-before-break source switching — **Decided**

1. The incoming source must report healthy and deliver at least one complete state sample before the
   outgoing source is dropped. If it never does, the outgoing source is kept.
2. At the switch instant the arbiter snapshots the set of controls **held** on the outgoing source.
   Every such control is marked _suppressed-until-release_ on the incoming source: no press edge is
   emitted, no release edge is emitted, and the control becomes eligible again only after the
   incoming source observes it released — or after a 2 s bound, after which it is treated as
   released.
3. The virtual target receives exactly one neutral state during the switch window, and active rumble
   is stopped. No held control leaks to the game across a switch.
4. Failure handling: incoming source never healthy ⇒ keep outgoing. Outgoing source already dead ⇒
   publish neutral, mark the source `Faulted`, keep keyboard and touch usable, show a warning. A
   control is never left latched in either direction.

This applies identically to managed→SDL, SDL→managed, and managed→managed (device generation
change).

### P0-025 · Knowing the controller is available to an external owner — **Decided**

WSGM asserts availability only from facts it can observe about **its own** state:

1. The plugin reports physical acquisition released and all handles closed.
2. The original controller mode is restored and re-enumeration is observed at the same physical USB
   location (`P1-032`).
3. Every WSGM-owned HidHide entry is removed and HidHide reports the device is no longer hidden by
   WSGM.
4. The device is visible through ordinary user-mode enumeration.

All four ⇒ the device is reported as **released and available**. WSGM never checks whether Handheld
Companion or any other manager actually acquired it, never waits for an external owner, and never
probes another process's ownership — that would be exactly the external-manager coupling `INV-011`
prohibits.

If (2) or (3) cannot be verified within the `P0-013` budget, the journal records
`handoff-unverified` and the Device page carries that warning until the next successful
reconciliation.

## P0.3 Legal, trust, dependency, and release policy

### P0-036 · License — **Decided 2026-08-27: GPL-3.0-or-later**

WSGM is relicensed from its previous "MIT with an OEM-preinstallation restriction" terms to **GNU
General Public License v3.0 or later**.

Relicensing audit result: the maintainer is the sole copyright holder to date, so no contributor
consent is required. `LICENSE` now carries the verbatim FSF GPL-3.0 text; `README.md` carries the
copyright line and the standard "version 3 or (at your option) any later version" grant.

**The OEM-preinstallation restriction is dropped, deliberately.** GPL-3.0 §7 forbids additional
restrictions on the rights it grants — a recipient is entitled to remove such a term — so "GPL-3.0 +
OEM clause" is not a valid GPL license. No separate proprietary OEM licensing track is established.
An OEM may therefore preinstall WSGM, but only under GPL terms: complete corresponding source for
their version, no added restrictions, and the same rights passed on to device buyers.

**License compatibility is only a question for artifacts WSGM actually ships or copies.** Reading
another project to learn what the hardware does — a WMI data address, a report prefix, a method ID,
a buffer length, a zone count, a command sequence, the shape of a workaround — and then implementing
it independently is not a licensing matter at all. Those are facts about MSI's hardware; none of
these projects can license them in the first place, and no compatibility analysis applies to using
them. `claw-8-a2vm-plugin.md`'s facts-versus-expression rule is the governing rule and this decision
does not change it.

| Input                                  | Relationship to WSGM                    | License question                                                                    |

### P0-043 · Publisher identity and signature policy — **Decided**

- Identity: an Authenticode-signed package; the publisher is the certificate subject, pinned in the
  installed package record on first install.
- Verification: at install, at enable, and at every activation. A package whose signature no longer
  verifies does not activate.
- Key rotation: a new certificate for an existing package ID requires explicit user confirmation
  naming both the old and new publisher. It is never silent.
- Downgrade: refused by default. An explicit user action may install an older version; it clears any
  staged update and is recorded.
- Revocation: a revoked or expired-and-not-timestamped signature disables the package at next
  device-cycle start, retains its configuration, and reports `package-signature-invalid`.
- Rollback: the previously installed version is retained until the replacement activates
  successfully once; a failed first activation offers a one-click rollback.
- Compromised publisher: WSGM ships no revocation list of its own. A `WSGM-reviewed` package is
  removed by a WSGM update; any other tier relies on certificate revocation plus the user's removal
  action.

### P0-044 · Reviewed privileged-helper policy — **Decided**

For 2.0 **no privileged helper is approved and none is planned**: the reviewed first-party host
inherits WSGM's elevation, which is what `[HW 2026-08-27]` showed is actually required. The policy
below exists so that a future helper cannot be introduced informally.

A privileged helper may be approved only when: it belongs to a `WSGM-reviewed` package; it exposes a
fixed, device-scoped operation set with no arbitrary register, buffer, method, IOCTL, path, script,
or executable parameter; it independently validates board, firmware, ranges, lengths, rate, and
current ownership on every call; it is safe when invoked by any other same-user process; it is
installed in an administrator-protected location with ACLs preventing non-administrator write; it is
hash- and signer-pinned by the package; and it is removed by WSGM uninstall. Approval requires a
written review against that checklist recorded in the package's review entry.

## P0.4 Runtime authority, shutdown, and remaining boundaries

### P0-047 · The authoritative device-cycle owner — **Decided**

The device cycle is owned by **the single WSGM process that owns a resident `ShellSession` in shell
or boot mode**, and by no other process, ever.

- **Election:** that process already holds WSGM's shell single-instance mutex. Device ownership is
  bound to it — a per-session named object `Local\WSGM.DeviceOwner.<sessionId>` is created by the
  same process that wins the shell mutex, and its existence is what other processes discover.
- **Discovery:** any other WSGM process opens that object to learn an owner exists, and connects to
  the owner's diagnostics pipe read-only.
- **No takeover:** there is no election contest, no handoff, and no takeover path. A second shell
  instance is already prevented; a non-shell mode never competes.
- **"WSGM exits"** means: the device-owner process exits. Other WSGM processes exiting is not a
  device-cycle event.

Per-user and per-session: the object name is session-scoped, so a second interactive session gets
its own owner. Only one device cycle exists per session, and the plugin's per-resource ownership
conflicts detect any cross-session contention as an ordinary conflict.

### P0-048 · `--settings` and `--overlay-test` safety — **Decided**

Neither mode ever creates the device-owner object, spawns DeviceHost, changes HidHide, creates a
virtual target, or touches hardware.

- **`--settings`** may connect **read-only** to an existing owner to display device status, plugin
  identity, and health. Changing the Device Integration or controller-management toggle from a
  standalone Settings process writes configuration and **requests** the change from the owner; the
  owner performs the transition. With no owner running, the toggle only writes configuration and
  takes effect at the next shell start.
- **`--overlay-test`** stays completely hardware-free. It renders overlay surfaces against a
  **simulated capability provider** and does not connect to a live owner at all.

Tests assert both: `--settings` and `--overlay-test` produce no DeviceHost process, no HidHide
mutation, and no virtual target, and `--overlay-test` opens no IPC connection.

### P0-049 · Bounded shutdown ownership and deadlines — **Decided**

| Exit path            | Sequence                                                           | Budget | On failure                                                  |
| -------------------- | ------------------------------------------------------------------ | -----: | ----------------------------------------------------------- |
| Normal exit          | Full `P0-013` A–D                                                  |   15 s | Journal, force host exit, warn at next start                |
| Update exit          | Full `P0-013` A–D, compressed                                      |   10 s | Same                                                        |
| Logoff / session end | Compressed: neutralize, request release, remove HidHide, kill host |    5 s | Journal; reconcile at next start                            |
| Uninstall            | Request graceful stop, wait                                        |   20 s | See below                                                   |
| Crash / forced kill  | None possible                                                      |      — | Kill-on-close job removes the host; reconcile at next start |

**No production hardware write may begin** unless the plugin can complete it or journal it within
the remaining phase budget. This is a plugin-side precondition checked before every write, not a
WSGM-side timeout.

The uninstaller is the one component that acts after graceful cleanup fails, and its authority is
narrow: using the recovery journal it may remove **WSGM-owned HidHide entries and the WSGM virtual
target**, because leaving those behind would permanently hide the user's controller with nothing
left to reconcile them. It must **never** attempt hardware restoration — fan tables, power limits,
lighting, and controller mode are the plugin's, and the plugin is gone.

### P0-050 · Proprietary OEM artifacts — **Resolved**

No proprietary OEM DLL, provider, driver, helper, firmware, or asset is redistributed without
documented rights. Externally installed prerequisites (`installOwner: oem-installed`) are modelled
separately from redistributable audited components (`installOwner: wsgm-installer`), and validation
rejects a package that treats one as the other (`P0-045`).

### P0-051 · OEM2 behavior when Steam's QAM is unavailable — **Decided**

One press, one immediate bounded action, no queue and no replay:

1. Steam is running in Big Picture **and** the QAM patch reports healthy ⇒ toggle Steam's native
   QAM.
2. Otherwise ⇒ toggle the **WSGM overlay on the Device page**, exactly once.
3. If the overlay cannot open either ⇒ log and no-op.

WSGM never launches Steam, never foregrounds Big Picture, and never queues the action for replay
when Steam becomes ready. A press that arrives during a mode transition is dropped, not deferred.

Rejected alternative: a plain no-op when Steam's QAM is unavailable. A hardware button that
sometimes does nothing reads as broken, and the WSGM overlay is the design's own "complete device
control surface" — falling back to it is the least surprising behavior and needs no new UI.

| Steam selectors, injection, CSS template, per-tier verification                                   | WSGM   |
| Avalonia glyph rendering and the existing `GlyphIcon` fallback                                    | WSGM   |
| Native Steam glyphs as the fail-open fallback                                                     | WSGM   |

**What a plugin may supply.** Two things, both data:

1. **Assets**, referenced by content hash from the package manifest, never by plugin-supplied path
   or URL. PNG is accepted within decode bounds. SVG is accepted only through WSGM's
   parse-and-re-emit normalizer: WSGM parses it against an allowlist of geometry elements and
   attributes and **re-serializes from its own model**, so the plugin's bytes never reach a CEF
   context or an Avalonia surface. `script`, `style`, `foreignObject`, external `image`/`use`
   references, `on*` handlers, entity declarations, and any external URL are rejected outright — a
   package containing one fails `wsgm-device pack`.
2. **A declarative control map**: schema-versioned JSON naming which canonical and OEM controls the
   device physically has, which asset renders each one, which side each rear control is on, and a
   bounded plain-text physical label per control. Labels follow `P1-012`'s existing rule for
   untrusted device-specific names — length-bounded, escaped at every sink, never markup.

**What a plugin still may not supply**, unchanged: CSS, JavaScript, XAML, HTML, URLs, Steam
selectors, patch logic, or anything executable. `INV-009` is narrowed, not repealed — see below.

**Bounds**, enforced at pack time and re-checked at load: per-asset bytes, per-profile total bytes,
asset count, image dimensions, control-map size, and label length. A profile that exceeds any bound
is rejected as a whole rather than truncated; the device falls back to native Steam glyphs.

**Why the CEF layer stays with WSGM.** The maintenance saving is real for artwork and illusory for
selectors. Steam's controller UI depends on hashed class names, inline SVG path data, and the
current DOM, so it breaks on Steam updates. One WSGM-owned adapter is fixed once and every device
benefits; N plugin-owned adapters break N times per Steam update, maintained by N people, none of
whom we can patch. Total maintenance rises and the failure is user-visible as "WSGM broke my
glyphs".

The security consequence is decisive now that `D5` ships in 2.0 (`P0-021`). Sideloaded and
signed-external packages are spawned de-elevated specifically so unreviewed code cannot reach
privileged surfaces. CEF injection bypasses that boundary completely: Steam's CEF context is the
user's authenticated Steam client, so script there is account-level control, and style alone
suffices to exfiltrate through selector-triggered `url()` requests or to overlay a convincing
credential prompt. Plugin-supplied CEF content would be the one path granting an unreviewed package
more reach than its own host has.

**`INV-009` is amended** from "never let a device plugin supply … SVG, URLs, arbitrary artwork …"
to:

> A device plugin may never supply XAML, HTML, CSS, JavaScript, URLs, arbitrary commands, or an
> arbitrary privileged operation. It may supply artwork and a declarative control map only as
> schema-validated, size-bounded, hash-pinned data that WSGM parses, normalizes, and re-emits from
> its own model before any surface consumes it.

**Backlog consequences:**

- `P8.1` (upstream pin, provenance, immutable inventory), `P8.2` (WSGM semantic catalog), `P8.3`
  (A2VM profile verification and conditional fork) and `P8.11` (reviewed catalog update workflow)
  are removed as WSGM work. `P8.2` is replaced by a schema-and-validator task.
- `P0-039`'s glyph-provenance audit moves from a WSGM-wide obligation to the Claw plugin package.
  The upstream Handheld Controller Glyphs MIT artwork is still the A2VM's source; it now ships
  inside that first-party package and carries its notice and `P0-041` provenance fields there. The
  credited upstream third-party artwork still needs checking — by the package author, before that
  package is published.
- `P2-108` and `P2-109` change target: Device Lab no longer recommends a WSGM catalog profile, it
  scaffolds an **empty** control map that the plugin author fills and visually verifies. The
  fail-closed rule is unchanged — an unverified map means native Steam glyphs, never a near match.
- New work: the SVG normalizer and its fuzz/malicious-input tests, the control-map schema, and the
  pack-time and load-time validators.
- **The `WSGM.Glyphs` project is dropped**, and so is the `third_party/` upstream snapshot. With
  artwork and the control map owned by the plugin, no WSGM-side glyph component is large enough to
  want its own assembly: the schema, validator, and SVG normalizer go into `WSGM.Device.Contracts`
  (shared by pack-time Device Lab and load-time WSGM), the Steam patch becomes one `ISteamUiPatch`
  in the `P7` Steam UI host, and rendering extends the existing `GlyphIcon` in `src/WSGM/Controls`.
- **The SDK owns the authoring side, never the injector.** `WSGM.Device.Sdk` gives plugin authors
  the control-map builder, asset packaging helpers, local validation, and a preview against a
  simulated Steam layout. It must not contain selectors, CDP calls, or patch apply/verify: the SDK
  is linked into the plugin, so anything in it runs with the plugin's authority, and putting the
  injector there would restore exactly the reach this decision removes.

**Unchanged by this decision:** `P0-005` presentation authority, `P0-017` selection precedence and
persistence, patch tiering and independent health (`P8.7`), bounded CEF asset delivery and cleanup
(`P8.8`), and CSS Loader coexistence (`P8.9`). Where those refer to "the WSGM catalog", read "the
active plugin's validated profile".
