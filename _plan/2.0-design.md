# WSGM 2.0 design

Status: lean architecture baseline, rewritten 2026-08-28

Branch: `2.0`

Reference device: MSI Claw 8 AI+ A2VM (`MS-1T52`)

## Goal

WSGM 2.0 turns the existing Windows Steam Game Mode shell into a complete handheld gaming layer
without turning it into an enterprise platform. It remains a small application for one owner, one
gaming PC, one active handheld, and one installed Device Plugin.

The design favors direct code, a small number of durable boundaries, and recovery from failures the
project has actually observed. It does not create governance, compatibility, or security machinery
for hypothetical deployment models.

## Feature scope is fixed

Architectural simplification must preserve every item below:

- Optional device integration and a real public Device SDK for community plugins.
- Full MSI Claw 8 AI+ A2VM support: identity, power, fans, telemetry, controller modes, physical
  input, rumble, motion, OEM buttons, firmware shortcut suppression, RGB, profiles, diagnostics,
  suspend/resume, and clean handoff.
- Optional WSGM controller management through HIDMaestro.
- Steam Deck Composite, Xbox 360, and DualShock 4 virtual targets.
- Global and per-application controller-target selection.
- WSGM-owned HidHide changes, managed UI input, virtual-target neutralization, and the existing
  SDL/Steam Input lease fallback.
- A persistent Steam CEF connection and narrow native-QAM restoration.
- RTSS frame-limit, overlay-level, profile, and performance integration.
- Frametime-driven AutoTDP with per-game learning, bounded power control, manual override, replay,
  diagnostics, and restoration.
- Physical handheld glyphs in Steam and WSGM surfaces, supplied by the active plugin as static data.
- The final Home, Steam, Device, and System overlay information architecture.
- Device Lab inventory, capture, correlation, known-device matching, safe probes, scaffolding,
  validation, and packaging through straightforward GUI and CLI workflows.
- Installer, update, uninstall, recovery, logging, and device/live validation needed to ship the
  preceding features reliably.

None of these features may be removed merely to make the architecture smaller.

## Product boundaries

### WSGM remains useful without Device Integration

Game Mode, Big Picture, shell/session transitions, storage, artwork, launch fixes, and the existing
overlay continue to work when Device Integration is off or no plugin is installed.

Device Integration is optional. Controller management is its optional child:

| Device Integration | Controller management | Result |
| --- | --- | --- |
| Off | Off | External software may own the handheld |
| On | Off | The plugin owns hardware; external software may own controller emulation |
| On | On | WSGM owns hardware and virtual-controller presentation |
| Off | On | Invalid and normalized to Off/Off |

### Exactly one installed Device Plugin

WSGM does not select between plugins and does not support simultaneous handhelds.

- Zero installed plugins: normal WSGM starts; Device Integration is unavailable.
- One installed plugin: WSGM validates and uses that package.
- More than one installed plugin: normal WSGM startup refuses before creating `ShellSession` or
  `DeviceHost`, and the error lists the conflicting package names and paths.

Counting happens before device matching. Different target models, disabled packages, older
versions, or a developer package still count. A plugin owns the complete handheld and any attached
device-specific resources it supports.

Recovery-first commands, setup, update cleanup, uninstall, and `--restore-shell` remain available
even when the plugin directory is invalid. Plugin updates stage outside the discovery directory and
replace the single installed package atomically.

### Runtime scope

When enabled, the one device cycle starts asynchronously with WSGM and spans Desktop Mode, Game
Mode, games, Steam restarts, and shell transitions. It ends only when the owning WSGM process exits
or the user turns Device Integration off.

An unexpected host exit is a recoverable fault inside the same cycle. It is not a second lifecycle,
an automatic external-manager handoff, or a reason to block WSGM startup.

### Deliberate non-goals

- Multiple installed or active Device Plugins.
- Multiple concurrently managed handhelds.
- A cloud plugin marketplace or runtime downloader.
- Automatic plugin promotion, publisher governance, or a WSGM revocation service.
- Sandboxing deliberately malicious local code.
- A generic elevated hardware broker or raw hardware API.
- Multi-launcher support; WSGM remains Steam-exclusive.
- A general controller, keyboard-macro, gyro, or touch remapper.
- Global SteamOS or Steam Deck spoofing.

## Smallest durable architecture

WSGM 2.0 adds only the boundaries required by NativeAOT, unstable vendor dependencies, and public
plugin development.

```text
WSGM.exe
  UI, session ownership, profiles, controller policy, CEF/QAM, RTSS, AutoTDP
      |
      | small exact-version named-pipe protocol
      v
WSGM.DeviceHost.exe
  loads the one installed Device Plugin and contains its crash/dependency failures
      |
      v
Device Plugin
  detects and owns one handheld's hardware implementation
```

The existing `WSGM.Launch` and `WSGM.LogonService` retain their current narrow responsibilities.

### Project responsibilities

| Project | Responsibility |
| --- | --- |
| `WSGM` | Product runtime, UI, semantic routing, controller targets, Steam/RTSS/AutoTDP |
| `WSGM.Device.Sdk` | One AOT-safe public API: DTOs, exact wire model, plugin interface, TestKit, and validation |
| `WSGM.DeviceHost` | Load one plugin, relay messages, supervise one process lifetime |
| `WSGM.DeviceLab` | One developer tool with GUI and CLI modes |
| `plugins/*` | Independent device implementations using the SDK |

Separate CLI, GUI, Core, ProbeHost, generator, and policy projects are not architectural goals.
Code may remain separated when it materially improves reuse, but project boundaries must not exist
only to enforce a diagram.

### Dependency direction

- `WSGM` references only the AOT-safe `WSGM.Device.Sdk` from the device platform.
- DeviceHost references the SDK, then loads the one package.
- Device Lab references the SDK and keeps its developer-only helpers internal.
- Plugins reference SDK and may use whatever ordinary libraries their hardware requires.
- No plugin or developer tool is copied beside the NativeAOT `WSGM.exe`.

## Device SDK and plugin contract

The public contract is intentionally small:

1. Read a minimal package manifest.
2. Detect the exact device.
3. Start and stop the plugin lifecycle.
4. Publish semantic capabilities and their state.
5. Receive validated semantic commands.
6. Publish canonical controller/motion/OEM input.
7. Receive canonical rumble or haptic output.
8. Expose bounded diagnostics.

WSGM defines what a capability means. The plugin owns how it works, including hardware identity,
transports, ranges, ordering, readback, restoration, and recovery. WSGM does not prescribe a
transport/protocol/layout/policy module hierarchy inside community plugins.

The installed WSGM, DeviceHost, SDK contract, and plugin must use the same exact integer API/wire
version. For 2.0 there is no forward/backward schema-negotiation matrix or mixed-component mode.

## Plugin installation and trust

A Device Plugin is executable hardware-control code, not passive theme data.

- Installation and removal are explicit user actions.
- Normal plugins live in one administrator-protected plugin slot.
- WSGM never downloads or silently updates plugins.
- The host is a crash/dependency boundary, not a malware sandbox.
- A plugin installed into the protected slot may run with the privilege WSGM already has because
  real hardware providers, including MSI WMI, require it.
- Developer builds use an explicit developer command/session and never replace the normal slot
  silently.
- Package ID, API version, entry assembly, paths, and basic file integrity are validated to catch a
  broken installation; WSGM does not implement certificate promotion, revocation, trust tiers, or
  independent package rollback.

The security boundary is simple and honest: an unprivileged process must not be able to replace code
that WSGM later loads elevated. A user who deliberately installs a plugin is choosing to trust it in
the same way they trust other administrator-capable handheld software.

## Device capabilities and UI

The semantic model covers the features WSGM actually renders:

- Sustained/slow/fast/peak power limits and OEM scenario mode.
- Fan mode, duty, target RPM, curves, measured RPM, and temperatures.
- Charge limit, charge protection, and bypass where supported.
- Lighting power, brightness, zones, colors, effects, and speed.
- Hardware telemetry.
- Physical controller input, motion, rumble/haptics, and OEM controls.
- Device-specific toggles, ranges, choices, actions, and read-only values.
- Physical handheld glyph profile and static assets.

Descriptors carry stable IDs, display metadata, supported operations, ranges, steps, units, and
availability. State carries current value, freshness, command progress, and an ordinary unavailable
or error reason. Do not create parallel evidence grades, desired-state generations, or result
taxonomies unless a current feature cannot be expressed without them.

The WSGM overlay contains every active handheld control. Settings contains ownership, startup,
integration, logging, and update policy only.

## Controller integration

The physical and virtual sides remain independent:

```text
plugin physical input -> canonical state -> WSGM input arbiter -> selected HIDMaestro target
selected target output -> WSGM output router -> plugin physical output
```

Required targets are Steam Deck Composite, Xbox 360, and DualShock 4. WSGM stores a global default
and direct per-application overrides. Only one virtual target exists at a time.

When a WSGM surface owns input, the arbiter routes canonical input to UI navigation and holds the
virtual target neutral until used controls are released. If managed input is unavailable, WSGM uses
the existing SDL plus Steam Input lease path. Steam's own QAM continues to receive the virtual
controller.

HidHide changes are an owned delta: WSGM adds and removes only its entries. Controller disable and
full device stop use the same make-safe sequence: neutralize target, let the plugin release and
restore physical input, then remove the virtual target and WSGM's HidHide entries.

## Steam UI, RTSS, and native QAM

WSGM keeps one persistent CDP connection owner with reconnect and context replacement handling.
Built-in patches use a small common lifecycle: probe, apply, verify, remove. Each patch fails
independently and native Valve UI remains the fallback.

Native-QAM controls include:

- TDP and current power state.
- RTSS frame limit and performance-overlay level.
- Performance profile and supported metrics.
- Controller target.
- AutoTDP state and direct enable/pause controls where the native component can support them.

The QAM and overlay call the same application services. There is no QAM-specific device,
controller, RTSS, or AutoTDP implementation. Steam receives only fixed semantic actions; no plugin
gets a JavaScript, CSS, filesystem, process, or raw-device bridge.

## Frametime-driven AutoTDP

AutoTDP is a required product feature, implemented as one session-owned service:

- Consume verified foreground-application frametimes.
- Respect the plugin's current minimum, maximum, and step for the primary power limit.
- Raise power quickly after sustained deadline misses.
- Lower power through settled one-step probes after stable periods.
- Restore the last known good value when a downward probe harms frame delivery.
- Recognize capped/menu states without driving immediately to maximum power.
- Learn per application and relevant display/target context from accepted samples.
- Pause on manual power changes and resume only through an explicit policy.
- Permit only one power command at a time and restore the underlying manual/profile value on stop.
- Provide deterministic replay, diagnostics, cancellation, and exact disable/exit cleanup.

The control algorithm uses frametime behavior, not guessed CPU/GPU utilization. It may grow in
sophistication only when recorded traces prove the simpler controller insufficient.

## Physical handheld glyphs

The active plugin supplies a static, declarative glyph package: profile metadata, controller
artwork, individual control assets, and a logical-to-physical map. WSGM validates formats, sizes,
control IDs, and package locality for reliability, then adapts those assets to Avalonia and Steam.

Plugins do not supply Steam selectors, JavaScript, runtime CSS, XAML, URLs, or commands. WSGM owns
the small Steam-build adapter and its fallback behavior. Physical presentation remains independent
from virtual target identity and Steam Input bindings.

Automatic exact-device selection is the default. Native Steam glyphs are the fallback, and a manual
reviewed profile remains available for diagnosis.

## Device Lab

Device Lab remains a real SDK companion, not a release-governance system. One JIT-capable tool may
offer GUI and CLI modes for:

- Machine, firmware, PnP, HID, WMI, controller, sensor, and dependency inventory.
- Matching against simple known-device definitions.
- Passive capture and timeline correlation.
- Explicit known read probes.
- One explicit attended semantic action at a time, with plugin-owned original-state capture,
  verified readback, and verified restore/release.
- Scaffold generation from confirmed observations.
- Fixture extraction and replay.
- Plugin validation, local run, and packaging.
- Sanitized export with obvious removal of machine/user identifiers.

The tool does not need trust promotion, evidence-grade enforcement, a general recipe authority
model, a separate privileged broker, or a compliance dossier. Imported files never become commands;
attended actions are compiled code started by an explicit local selection and confirmation.

## Overlay overhaul

The final top-level destinations remain:

| Destination | Responsibility |
| --- | --- |
| Home | Steam/session state, transitions, warnings, immediate actions |
| Steam | Library, storage, artwork, and launch configuration |
| Device | Hardware, profiles, controller, motion, OEM, lighting, glyphs, diagnostics |
| System | Power state, wake locks, Task Manager, and system actions |

Pages consume shared application services. They do not own device, CEF, RTSS, controller, or
AutoTDP policy. Preserve controller-first navigation, touch, Back behavior, focus/scroll
restoration, scaling, accessibility, and the existing feature set while replacing the current
catch-all layout.

## Reliability and safety without ceremony

Complexity is justified only when it prevents a concrete failure:

- Exact device/firmware gates and bounded hardware values.
- Serialized vendor calls and cancellation.
- Original-state capture and restoration for values WSGM changes.
- A compact recovery journal for unresolved hardware or HidHide ownership.
- DeviceHost crash isolation.
- Input failover before releasing a hidden physical controller.
- Asynchronous feature startup so Game Mode is never blocked.
- Per-patch Steam failure isolation and native fallback.
- Clear diagnostics for remote device reports.

The following are not release requirements:

- Generated requirement-to-code traceability.
- A test for every DTO field or theoretical ordering.
- Formal package promotion/revocation workflows.
- Security claims against malicious same-user or administrator code.
- Reproducible evidence bureaucracy around ordinary local development.
- Multiple layers that only translate one internal representation into another.

## Delivery sequence

1. Simplify the current architecture and remove governance/build/test machinery that serves no
   product feature.
2. Stabilize the thin SDK, one-plugin loader, DeviceHost lifecycle, and Device Lab developer flow.
3. Finish and validate the Claw implementation and clean device/controller handoff.
4. Finish all controller targets, per-app selection, managed UI input, output, and HidHide behavior.
5. Finish the persistent Steam host, native QAM, RTSS, performance stream, and AutoTDP.
6. Finish plugin-owned physical glyph delivery in Steam and WSGM.
7. Finish the overlay information architecture without duplicating services.
8. Validate installer/update/uninstall, live Steam, reference hardware, performance, recovery, and
   the final artifact.

## Completion

WSGM 2.0 is complete when the full fixed feature scope works smoothly on the reference Claw, the
SDK lets another developer build and run a plugin without learning an internal governance system,
normal startup refuses ambiguous multi-plugin installations, failures return to usable input and
native Steam UI, and the installer can update or remove WSGM without leaving owned hardware or
system state behind.
