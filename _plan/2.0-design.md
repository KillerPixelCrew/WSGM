# WSGM 2.0 Design Plan

Status: Design baseline  
Branch: 2.0  
Initial reference device: MSI Claw 8 AI+ A2VM

## Purpose

WSGM 2.0 expands Windows Steam Game Mode from a Steam-focused shell into an optional, integrated handheld platform layer while preserving the lightweight core for users who prefer Handheld Companion or another hardware manager.

The design has four implementation pillars:

1. An optional, community-extensible device plugin and capability system.
2. An optional HIDMaestro virtual-controller backend.
3. A robust Steam CEF host that restores Valve's OS-gated Quick Access Menu controls on Windows.
4. A major WSGM overlay overhaul built around the resulting device capabilities.

The pillars are ordered deliberately. The final UI must be designed around the completed capability model rather than forcing new features into the current navigation.

## Product boundaries

### WSGM core remains independently useful

The existing Game Mode, Big Picture, session transition, shell, library, storage, artwork, launch-fix, and overlay features remain usable without any WSGM-managed handheld hardware.

Device integration must never become a prerequisite for entering Game Mode.

### Optional ownership

WSGM must support these configurations:

| Device integration | Virtual controller | Intended owner |
| --- | --- | --- |
| Off | Off | Handheld Companion or another external manager owns the handheld |
| On | Off | WSGM owns hardware control; an external application owns controller emulation |
| On | On | WSGM owns hardware control and virtual-controller presentation |
| Off | On | Invalid configuration |

Device integration is the parent capability. Virtual-controller management cannot be enabled without it.

### Runtime scope

The device subsystem lifecycle is bound to the WSGM process, not to Game Mode.

When WSGM starts with Device Integration enabled, the device host starts asynchronously and remains active across Desktop Mode, Game Mode, games, Steam restarts, and transitions between them. The complete Device overlay is available in Desktop and Game Mode; Steam's native QAM is only an additional Game Mode projection of the same state.

The device cycle has exactly two terminal triggers:

1. WSGM exits.
2. The user turns Device Integration off in Settings during the run.

An unexpected DeviceHost exit is a fault within the same device cycle. WSGM applies bounded restart, backoff, or quarantine; it does not treat the crash as an intentional deactivation or handoff.

Leaving Game Mode, closing a game, restarting Steam, disabling only WSGM controller management, a temporarily degraded capability, or an individual resource conflict must not stop or recreate the device host. Turning off controller management uses the same two-phase handoff as full deactivation: WSGM neutralizes its virtual target while keeping HidHide active, the plugin releases and restores only its physical-controller resource, and WSGM then removes the virtual target and HidHide state. The plugin host and every noncontroller resource continue.

### Conditional dependencies

Optional components must be installed only when required. A user who disables WSGM device integration must not be required to install HIDMaestro, usbip-win2, HidHide, PawnIO, or other device-layer dependencies.

Device-specific providers, libraries, signed helpers, and drivers belong to the plugin that requires them. A plugin declares those dependencies but cannot install or repair them at runtime. WSGM may install only separately audited components with pinned versions, hashes, signers, licenses, and removal behaviour.

Previously installed components may remain installed but inert. Removal can be offered separately and must not be required merely to disable a feature.

## Hard UI boundary

Everything that controls the handheld lives in the WSGM overlay.

The Settings window configures WSGM itself and never becomes a secondary handheld control center.

| WSGM overlay                    | Settings window                        |
| ------------------------------- | -------------------------------------- |
| TDP and power limits            | Startup and auto-launch                |
| Fan modes and curves            | Game Mode and session behaviour        |
| Charge limits                   | Hotkeys and swipe gestures             |
| Controller target               | Overlay appearance                     |
| OEM-button assignments          | CEF integration enablement             |
| Lighting and device features    | Device-integration master toggle       |
| Hardware profiles               | Controller-management ownership toggle |
| Sensor calibration              | Updates, logging, and WSGM diagnostics |
| Active device and plugin status | Home application configuration         |
| RTSS overlay and frame limit    | General WSGM preferences               |

The master enable/disable switches are WSGM ownership settings and therefore belong in Settings. Once a subsystem is enabled, its actual device controls belong in the overlay.

## Pillar 1: device plugin and capability system

### Goals

The plugin system must be:

- Small enough for community contributors to understand.
- Friendly to LLM-assisted implementation.
- Declarative where hardware permits.
- Explicit about device identity and supported capabilities.
- Safe to activate and deactivate at runtime.
- Independent from the selected virtual-controller target.
- Capable of supporting additional handhelds without adding device conditionals throughout WSGM.

The MSI Claw 8 AI+ A2VM is the first reference implementation, not a hardcoded special case in shared services.

The detailed runtime boundary, compatibility-sweep workflow, known-implementation catalog, evidence format, and scaffold generator are defined in the [device plugin system and developer tooling plan](./device-plugin-system-and-tooling.md).

### Responsibilities

A device plugin owns:

- Device detection and identity.
- Every device-specific transport, protocol, layout, and command sequence.
- TDP and power-limit implementation.
- Fan control, fan curves, readback, and firmware release.
- Battery and charge-limit controls.
- Lighting and other OEM hardware features.
- Hardware telemetry.
- Physical controller input acquisition.
- Physical output and rumble encoding.
- OEM button sources and device-specific suppression.
- Hardware validation, sequencing, readback, rollback, and recovery journals.
- Device-specific dependencies and privileged components.
- Device-specific lifecycle and recovery behaviour.

WSGM owns the semantic capability schemas, first-party UI, desired values, profile selection, process supervision, virtual-controller system, HidHide transaction, input arbitration, and command/state presentation. It receives a capability such as a sustained power limit but does not know whether the plugin implements it through WMI, EC, AMD SMU, Intel MMIO, or another mechanism.

WSGM exposes no generic AMD/Intel TDP service, EC/PawnIO service, raw WMI/HID/IOCTL interface, or shared administrator-capable hardware broker to plugins. Reusable hardware code may be packaged as a versioned SDK library or implementation module linked into and owned by a plugin; it is not a WSGM runtime service.

### Activation contract

A plugin is not merely an assembly that is loaded and forgotten. It needs an explicit lifecycle:

- Detect.
- Activate.
- Report capabilities and current state.
- Suspend and resume.
- Deactivate.
- Release all handles and ownership.

Disabling device integration must:

1. WSGM stops accepting new semantic device commands, establishes an input fallback where needed, and neutralizes its virtual target while keeping HidHide in place.
2. The plugin stops physical-controller, OEM-input, motion, and output readers.
3. The plugin restores the original physical-controller mode, releases acquisition, and reports whether the resulting topology is verified.
4. The plugin restores or safely releases every other hardware resource it owns, closes its transports, and completes or preserves its recovery journal.
5. After the plugin acknowledgment or a bounded timeout, WSGM removes its virtual devices and only its HidHide configuration.
6. WSGM disposes the plugin host; a timeout is reported as an unverified handoff, never clean restoration.
7. Both sides leave Handheld Companion and other external tools untouched.

WSGM must not automatically terminate, reconfigure, or assume ownership of Handheld Companion.

### Capability-driven UI

Plugins advertise capabilities and valid ranges. The overlay renders the appropriate first-party controls.

A device plugin must not need to ship arbitrary overlay JavaScript or duplicate the WSGM visual language simply to expose a TDP slider, fan curve, charge limit, or lighting mode.

Immutable capability descriptors include enough information for validation and presentation, such as:

- Minimum and maximum.
- Step size.
- Units.
- Supported read, write, and action operations.
- Persistence behaviour.
- AC versus battery support.
- Whether a restart or device reset is required.
- Any mutually exclusive modes.

A separately versioned plugin state reports observed/applied hardware value, availability, hardware command status, quality, observation time, host/device generation, and structured unavailable or degraded reasons. WSGM's capability projection adds the authoritative requested/desired value, profile source, and UI command progress. WSGM validates IPC shape and UI consistency; the plugin performs authoritative safety validation again for every hardware command.

Each selected plugin runs in its own unelevated DeviceHost process. Process separation provides dependency and crash isolation, not a malware sandbox. A reviewed plugin that genuinely requires privilege may include a separately signed, fixed-operation, device-specific helper; WSGM does not elevate DeviceHost or expose a generic privileged channel to community code.

The exact package ABI, packaging format, version negotiation, signing/update workflow, and wider community trust policy remain implementation decisions to resolve during the first phase.

## Pillar 2: HIDMaestro virtual-controller backend

### Locked backend decision

HIDMaestro is the initial WSGM 2.0 virtual-controller backend.

Reasons:

- It is designed around data-driven controller profiles.
- Standard targets use an event-driven UMDF2/shared-memory path.
- It supports the multiple target types WSGM now requires.
- It already contains a full Steam Deck composite profile.
- Its MIT license is compatible with a permissive or GPL WSGM licensing direction.
- It exposes output events that WSGM can route back to physical hardware.
- VIIPER is similarly young and has already required local Steam Deck fixes, while its current Handheld Companion use has shown measurable CPU overhead.

HIDMaestro must be wrapped behind a WSGM-owned backend interface. Device plugins must never call HIDMaestro directly.

The stable boundary is:

Physical device plugin -> canonical handheld state -> WSGM controller adapter -> HIDMaestro target

This permits a future backend replacement without rewriting community device plugins.

### Initial targets

| Target | Purpose |
| --- | --- |
| Steam Deck Composite | Default Steam-focused target with Valve recognition and the richest handheld input model |
| Xbox 360 | Native XInput compatibility for older games, programs, and emulators |
| DualShock 4 | PlayStation Remote Play and software requiring a PlayStation controller |
| DualSense | Potential later target; not required for the first WSGM 2.0 milestone |

The full Steam Deck target currently uses HIDMaestro's composite usbip-win2 backend. Standard targets use HIDMaestro's UMDF2/shared-memory path.

Only one WSGM virtual controller may be active at a time. Keeping several targets connected risks duplicate input, unstable XInput slot assignment, ambiguous application binding, and HidHide conflicts.

### Target selection

WSGM should support:

- A global default target.
- Per-application target selection.
- A quick target selector in the native Steam QAM.
- The same target control in the full WSGM Device overlay.

A target change normally removes one virtual device and enumerates another. WSGM must surface when the current application may need to be restarted to bind the replacement.

### Canonical handheld state

The canonical state must represent the richest supported handheld input without assuming a particular virtual target:

- Standard buttons.
- D-pad.
- Sticks and triggers.
- Rear paddles.
- Gyroscope and accelerometer.
- Touchpads and touch contacts.
- Stick-touch sensors.
- OEM controls as a separate channel.
- Output and haptic events as a separate return channel.

A target consumes only the capabilities it genuinely supports.

### Explicit non-goals

WSGM 2.0 is not a general-purpose input mapper.

The following are out of scope:

- Arbitrary face-button remapping.
- Stick or trigger remapping.
- Gyro-to-mouse conversion.
- Gyro-to-stick conversion.
- Touchpad-to-mouse or touchpad-to-stick conversion.
- Synthesizing unsupported target capabilities.

Gyro is passed through only when the selected virtual target supports native motion input. Xbox mode does not convert gyro into another input type.

Calibration, dead-zone correction, range normalization, orientation correction, and hardware fault correction remain allowed because they correct the physical input rather than redefine its meaning.

### OEM-button exception

Only device-specific OEM controls may be remapped.

A plugin declares each OEM control with a stable identifier, display name, and type. Expected defaults include:

| OEM control             | Default action                                                 |
| ----------------------- | -------------------------------------------------------------- |
| Quick Access button     | Open or close Steam's native QAM                               |
| Control Center button   | Open or close the WSGM overlay                                 |
| Additional OEM controls | Device-specific action or user-configurable WSGM/system action |

OEM controls are separate from the ordinary game controller and do not justify adding a general mapping editor.

### HidHide ownership

When WSGM controller management is active, WSGM may hide the physical controller so applications see only the selected virtual target.

WSGM must:

- Track exactly which HidHide changes it owns.
- Remove only its own entries during deactivation.
- Never replace or normalize the full HidHide configuration.
- Leave HidHide completely untouched when controller management is disabled.
- Coordinate the two-phase handoff and require the active plugin to close its physical-controller handles before WSGM removes its HidHide entries.

### WSGM UI input and Steam Input lease policy

When WSGM controller-management mode has a healthy plugin-owned physical source, WSGM must navigate its own overlay, taskbar, and Settings surfaces from the plugin's canonical input. The original controller is hidden from ordinary applications through WSGM-owned HidHide state but remains readable by the allowlisted DeviceHost. These WSGM surfaces therefore do not acquire the Steam Input block lease.

A shared input arbiter chooses between:

- Managed canonical input from DeviceHost when controller-management mode has a healthy plugin-owned physical source.
- The existing SDL plus Steam Input lease path when controller management is off, externally owned, unsupported, or degraded.

Opening a WSGM surface claims a reference-counted local UI capture. The arbiter continues consuming the plugin's canonical input, sends a neutral state to the HIDMaestro virtual target, stops forwarding gameplay controls, and routes canonical events to WSGM navigation. It suppresses controls already held at open and keeps the target neutral until UI-used controls are fully released after the final WSGM surface closes. This prevents overlay navigation from also controlling the game or Steam behind it.

The local capture is internal to WSGM. It performs no Steam hook installation, HID-handle revocation, Steam controller recovery, device re-enumeration, or layout change.

Steam's native QAM is Steam-owned, not a WSGM-captured surface. It continues receiving the virtual controller and does not cause either a local WSGM capture or a Steam Input block lease.

The Steam Input lease subsystem remains a permanent WSGM capability. It continues to serve unmanaged/external controllers, degraded-source fallback, recovery paths, and separately scoped per-game launch scenarios. Managed surface input changes only when an overlay/taskbar lease is acquired; it is never a reason to delete, uninstall, or globally disable the lease infrastructure.

### Acceptance gates

HIDMaestro becomes the release backend only after validation on the MSI Claw:

- Steam recognizes the full composite target as a Valve Steam Deck controller.
- Gyro, touchpads, paddles, and stick-touch data behave correctly where supported.
- DualShock 4 is accepted by the official PlayStation Remote Play client.
- Xbox 360 is visible through native XInput to representative older software.
- Rumble and output events return to the physical device.
- Controller target switching has predictable device and player-slot behaviour.
- HidHide activation and cleanup are reversible.
- Managed WSGM surfaces consume physical canonical input without acquiring the Steam Input block lease.
- Local UI capture neutralizes the virtual target until every UI-used control is released, with no input leaking to the game.
- Steam native QAM continues to receive virtual-controller input.
- SDL/Steam-lease fallback and mid-surface source switching recover without duplicate presses or an input gap.
- Suspend/resume, forced process termination, and repeated enumeration recover cleanly.
- Idle and active CPU use are measured, including gyro and high report rates.
- The observed 4-6 percent Steam Deck target overhead from the current Handheld Companion/VIIPER setup is not reproduced without explanation.

## Pillar 3: native Steam QAM restoration

### Native-first principle

Most of the Steam Deck QAM implementation still ships in the Windows Steam client but is hidden or disabled by OS and device gates.

WSGM must revive Valve's existing components instead of recreating visual approximations.

For every feature, the preferred sequence is:

1. Locate and probe the existing Steam component.
2. Remove only the narrow Windows or capability gate that hides it.
3. Supply the missing state and action contract through WSGM.
4. Verify that the native component is healthy.
5. Use a WSGM-rendered replacement only if Valve genuinely removed the component.

This preserves Valve's native:

- Layout and visual design.
- Controller navigation.
- Animations.
- Localization.
- Accessibility behaviour.
- QAM sizing.
- Future UI improvements.

The existing Windows Wi-Fi icon restoration is the proven model: WSGM feeds Steam's existing store the data that the Windows backend omits rather than drawing a replacement icon.

Steam's controller-oriented CEF surfaces are also a first-class restoration target. WSGM will integrate the pinned MIT-licensed [Handheld Controller Glyphs](./controller-glyph-integration.md) artwork and mappings through its own patch host so Steam Input configuration, controller diagrams, and relevant Gamepad UI prompts match the verified physical handheld as they do with Decky/CSS Loader on SteamOS. This does not require Decky or CSS Loader and does not change the selected virtual-controller identity.

### No global SteamOS spoof

WSGM must not globally claim that Windows is SteamOS or that every machine is a Steam Deck.

A global spoof could activate unrelated Linux-specific power, storage, update, shutdown, or device behaviour.

Patches must be narrowly scoped to an individual route, component, store, action, or capability.

### Restored controls

Initial native QAM controls include:

| Native QAM control           | Windows implementation           |
| ---------------------------- | -------------------------------- |
| TDP slider and current value | Active WSGM device plugin        |
| Performance-overlay level    | RTSS configuration               |
| Frame limiter                | RTSS framerate limit             |
| Performance profile          | WSGM per-game settings           |
| Performance data             | RTSS and WSGM hardware telemetry |
| Controller target            | WSGM HIDMaestro adapter          |

The exact set can expand as live inspection confirms which native components remain available.

### QAM and overlay relationship

The WSGM overlay is the complete device-control surface.

It remains available in Desktop Mode and Game Mode throughout the active WSGM device lifecycle.

Steam's native QAM duplicates the small subset that is useful during gameplay.

| WSGM Device overlay                      | Steam QAM                 |
| ---------------------------------------- | ------------------------- |
| TDP                                      | TDP                       |
| Frame limit                              | Frame limit               |
| Performance-overlay level                | Performance-overlay level |
| Controller target                        | Controller target         |
| Fan curves                               |                           |
| RGB effects                              |                           |
| Charge limits                            |                           |
| Hardware profiles                        |                           |
| OEM-button configuration                 |                           |
| Device diagnostics and advanced controls |                           |

The shared controls use exactly one backend state and command implementation. A value changed in QAM must update the WSGM overlay immediately, and a value changed in the WSGM overlay must update QAM.

There is no QAM-specific TDP controller or overlay-specific RTSS controller.

### Interaction goal

The expected handheld flow is:

1. Press the physical QAM OEM button.
2. Steam opens its native QAM.
3. Adjust TDP, frame limit, RTSS overlay level, or controller target.
4. Press the same button again.
5. Return immediately to the game.

Because this is Steam's native QAM, Steam retains controller ownership and focus behaviour.

For RGB effects, fan curves, charge limits, hardware profiles, OEM assignments, and deeper configuration, the user opens the WSGM overlay instead.

### Robust CEF host

WSGM already has a live-verified route into Steam through the CEF remote-debugging endpoint. WSGM 2.0 should evolve this into a persistent, Decky Loader-style host rather than accumulating independent one-shot evaluations.

The host should provide:

- Steam target discovery and shape validation.
- Persistent CDP sessions where appropriate.
- Automatic reconnect after Steam or steamwebhelper restarts.
- Reinjection after target navigation or JavaScript-context replacement.
- Versioned and idempotent bootstrap code under the WSGM namespace.
- Request IDs, responses, notifications, cancellation, and timeouts.
- Patch health checks.
- Structural module discovery and fingerprints.
- A per-patch kill switch.
- Clear compatibility diagnostics after Steam updates.
- Safe coexistence with other CEF tools.
- An embedded TypeScript/React asset pipeline instead of growing C# string literals.

The implementation should evaluate CDP Runtime bindings before introducing an additional localhost RPC server. It must not add a new unauthenticated privileged endpoint.

The handheld-glyph patch uses the same host but remains independently versioned and removable. WSGM owns the Steam-build-specific selectors and delivers only the active, hash-locked profile assets; device plugins may select a reviewed semantic profile ID but cannot provide CEF CSS, JavaScript, URLs, or arbitrary artwork. Stable Steam glyph-URL mappings, controller diagrams, inline SVG replacements, and capability hiding have separate probes and health states.

Injected JavaScript must receive a narrow, versioned, allowlisted API. It must never receive a generic execute-command, arbitrary PowerShell, arbitrary filesystem, unrestricted plugin-call, or raw privileged-device interface.

### Patch lifecycle

Each native restoration should behave as an independent patch with:

- Stable patch identifier.
- Patch version.
- Probe.
- Apply.
- Verify.
- Remove.
- Compatibility fingerprint.
- Diagnostic result.
- Recovery and reapply behaviour.

A Steam update that breaks one patch must not disable every WSGM CEF feature or damage the native QAM.

### Startup invariant

CEF discovery, QAM restoration, patch probing, and RTSS detection must never block entering Game Mode. Device integration starts with WSGM regardless of shell mode and likewise must not block WSGM startup, the desktop overlay, or any Desktop/Game Mode transition.

WSGM launches or foregrounds Big Picture immediately. Restoration happens asynchronously after the correct Steam UI target is ready.

A failed or delayed patch produces a retryable warning and logs. It must never recreate the old long Back to Game Mode transition.

## Pillar 4: WSGM overlay overhaul

### Timing

The overlay overhaul is the final implementation phase.

The device capability system, controller state, native QAM surface, and RTSS contracts must stabilize first so the redesign reflects the real product rather than predicted controls.

### Information architecture

The current Session, Tools, and Power model is under pressure because Tools has become a catch-all.

The proposed top-level destinations are:

| Destination | Responsibility                                                            |
| ----------- | ------------------------------------------------------------------------- |
| Home        | Steam/session state, desktop transitions, warnings, and immediate actions |
| Steam       | Library tabs, storage, artwork, and per-game launch configuration         |
| Device      | Every handheld control and active-device state                            |
| System      | Power state, wake locks, Task Manager, and system actions                 |

The exact rail width, labels, responsive behaviour, and page layout require handheld wireframes and device testing before being locked.

Settings remains a separate WSGM configuration window and is not a Device page.

### Complete Device destination

The Device destination is the authoritative and complete handheld control center.

Expected internal sections include:

- Overview.
- Power and thermals.
- Controller.
- OEM controls.
- Lighting and device features.
- Profiles.
- Diagnostics.

The Controller section also previews and selects the physical handheld glyph profile used by Steam's CEF and WSGM surfaces. Automatic exact-device selection is the default, native Steam glyphs are the fail-open fallback, and a reviewed manual profile is available for diagnosis. This presentation setting never changes HIDMaestro target identity or Steam Input bindings.

The native QAM is a quicker duplicate surface for a few high-frequency controls; it does not remove those controls from the WSGM overlay.

### Navigation architecture

The redesign should replace one large visibility-switched window with a navigation shell and independent pages.

Desired properties:

- Capability-driven navigation visibility.
- Device destination absent when integration is disabled.
- Independent page views and view models.
- Lazy page creation where appropriate.
- A navigation stack for nested tools and editors.
- Correct Back/B behaviour.
- Focus and scroll-position restoration.
- Controller-first operation.
- Shared warning/status presentation.
- Reusable preview and input-testing surfaces.

The overlay and native QAM consume the same state services and command handlers. UI code must not own hardware, RTSS, controller, Steam transition, or plugin policy.

## Shared service boundaries

The main runtime data flow is:

Plugin-owned hardware implementation -> semantic IPC -> WSGM capability router -> overlay, native QAM, and profile policy

Physical controller input -> canonical handheld state -> input arbiter -> WSGM UI capture or HIDMaestro adapter -> selected virtual target

Virtual target output -> WSGM output router -> physical device plugin

RTSS -> performance service -> overlay and native QAM

Steam CEF -> Steam UI host -> allowlisted WSGM services

Pinned handheld artwork -> WSGM glyph catalog -> Steam Input CEF patch and first-party glyph service

The UI surfaces are clients. They never become independent implementations of device behaviour.

## Performance and reliability principles

WSGM 2.0 must prefer event-driven state propagation over fixed high-frequency polling.

Every repeating loop requires:

- A documented reason.
- A bounded frequency.
- A clear active versus idle policy.
- Cancellation and disposal.
- Measurement on the reference handheld.

Device, controller, CEF, and RTSS failures must degrade their feature rather than terminate the shell or block Game Mode.

All WSGM-owned state must have an explicit cleanup path for:

- Subsystem disable.
- Plugin-host failure or teardown.
- Controller target replacement.
- Suspend/resume.
- Steam restart.
- WSGM restart.
- Forced process termination where recoverable.
- Handoff to an external controller or device manager when Device Integration is disabled or WSGM exits.

Plugin runtime removal, update, or replacement is not an additional lifecycle trigger while Device Integration is active.

## Licensing direction

HIDMaestro is MIT licensed and usbip-win2 is BSD-2-Clause, so both are compatible with permissive and GPL-family WSGM directions.

A final WSGM relicensing decision remains open. Before selecting GPL-3.0-or-later or another license, the project must audit:

- Current WSGM license and contributor ownership.
- Whether every contribution can be relicensed.
- Required third-party notices.
- HIDMaestro redistribution or packaging terms.
- usbip-win2 redistribution and driver-package notices.
- Every plugin-packaged implementation module, native DLL, provider, signed helper, and driver.
- Any code learned from or incorporated from Handheld Companion and VIIPER.
- Handheld Controller Glyphs' MIT notice, pinned asset inventory, and credited upstream artwork provenance.

Reference implementations may be studied for architecture and protocol behaviour, but code reuse must follow the selected license and attribution requirements.

- Implement the single bounded-trial runner and use it for separately authorized A2VM power, fan, rumble, lighting, and controller-mode compatibility trials.
- Produce the first sanitized A2VM baseline capture and golden fixtures.
- Separate offline validation, live compatibility trials, hardware acceptance, and retail approval.
- Define canonical handheld input and output state.
- Define subsystem ownership modes.
- Build a minimal HIDMaestro adapter experiment.

- Prototype bounded glyph-asset delivery and tiered selector verification in the Steam Input CEF routes.
- Prototype RTSS state and control.
- Record signing, packaging, and licensing findings.

- Implement per-plugin DeviceHost supervision and semantic capability IPC.

### Phase 2: controller integration

- Integrate HIDMaestro behind the WSGM adapter.

- Implement Steam Deck Composite, Xbox 360, and DualShock 4 target selection.
- Implement HidHide ownership.
- Implement physical output routing.
- Add per-application and global target selection.

### Phase 3: Steam UI and performance

- Refactor the CEF route into the robust Steam UI host.
- Convert the Wi-Fi restoration into the first versioned patch.
- Probe and ungate the native performance page and controls.

- Connect TDP, performance, profiles, and controller target to native QAM.

### Phase 4: overlay overhaul

- Finalize handheld wireframes.
- Replace Tools with a durable information architecture.
- Build the complete Device destination.
- Split the monolithic overlay into independent pages and navigation.
- Reuse the shared backend contracts used by QAM.
- Reuse the reviewed physical-handheld glyph catalog for controller hints, OEM controls, input tests, and profile preview.
- Validate touch, controller, focus, scaling, and recovery on the Claw.

## Locked decisions

- Device integration is optional.
- The device lifecycle spans the full WSGM run and stops only on WSGM exit or the Settings master toggle.
- WSGM defines semantic capabilities; each plugin owns its complete hardware implementation.
- WSGM exposes no raw hardware API or generic AMD/Intel TDP, EC, WMI, HID, IOCTL, or privileged broker service to plugins.
- Each plugin runs out of process; DeviceHost is never elevated.
- Reviewed plugins may use separately signed, device-specific fixed-operation helpers when required.
- Device definitions compose reusable implementation modules instead of inheriting another model's hardware policy.
- Device Lab first matches and safely probes known implementations, then generates a fail-closed scaffold; deeper reverse engineering is secondary.
- Virtual-controller management is optional and depends on device integration.
- WSGM must coexist cleanly with Handheld Companion.
- HIDMaestro is the initial virtual-controller backend.
- Managed WSGM surfaces use direct physical input instead of the Steam Input surface lease.
- The Steam Input lease is a permanent capability for unmanaged-controller fallback, recovery, and per-game launch scenarios; managed UI input only changes its acquisition policy.
- Initial targets are Steam Deck Composite, Xbox 360, and DualShock 4.
- Only one WSGM virtual target is active at a time.
- WSGM is not a general controller or gyro remapper.
- Only OEM buttons may be remapped.
- The WSGM overlay contains every handheld control.
- The Settings window configures WSGM only.
- Steam's native QAM duplicates frequent in-game controls.
- Native Steam UI is revived before a replacement UI is considered.
- Steam Input and relevant Gamepad UI glyphs use a pinned, audited physical-handheld profile through WSGM's CEF patch host; this presentation never changes controller identity or mappings.
- WSGM must not globally spoof SteamOS or Steam Deck identity.
- Device and QAM initialization never block entering Game Mode.
- The overlay overhaul is the final WSGM 2.0 phase.
