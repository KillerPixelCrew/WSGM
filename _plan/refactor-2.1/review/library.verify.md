## Missed findings

### LIBRARY-V-001 (medium) An apply can make two titles own one Steam shortcut, with no adoption involved
- `Shell/GameLibraryService.cs:2014-2019` (Revalidate, Add branch) and `:1840-1841` (this run's own writes are folded into `existing`).
- The Add branch looks for a matching shortcut in all of `existing`, including shortcuts another title's record already claims. `ImportPlan.Build` excludes claimed shortcuts (`ImportPlan.cs:312-315, 612-614`); this branch bypasses that rule. Scenario: a GOG title and the `.lnk` to the same exe in a Start-menu folder source (or a `.exe` and a `.lnk` to it in one folder). `ShortcutFolderSource.Direct` composes the same Target and arguments (`ShortcutFolderSource.cs:225-243`), and `CommandShortcut.Same` ignores the start directory. Both show as preselected "New" (`ImportPlan.cs:565`). Applying them adds the shortcut for the first title, folds it into `existing`, then turns the second Add into `Update` of that same AppId. The second title's start directory overwrites the first's, and both records name one AppId. Removing either source later offers a `Remove` that deletes the shortcut the other title still claims (`ImportPlan.cs:368-382`). This is more likely than the reviewer's double-Adopt case (LIBRARY-002) because nothing has to be ticked by hand.
- Recommendation: in the Add branch, consider only shortcuts no other title's record claims. `ApplyCoreAsync` already holds `records` and updates it as it saves, so this removes a hole and adds no state. Settle it together with LIBRARY-002 and its question Q1, since the losing title's presentation is the same decision.

### LIBRARY-V-002 (medium) Every config.json reload resets the open artwork pages and wipes all provider caches
- `Shell/SteamArtworkBrowserSource.cs:650-677`, called from `ShellSession.Config.cs:144` on every reload, on the UI thread.
- Any WSGM setting commit reloads config: a library source toggle (`GameLibraryService.cs:571`), a theme, a sound pack or a Quick Access change. Each reload (1) calls `ArtworkSearch.ResetCaches()` unconditionally, once per open context plus once more for the parent (LIBRARY-012 noted only the repetition). That drops SteamGridDB and Screenscraper answers and remembered failures, which spends Screenscraper's daily allowance again. `GameLibraryArtwork.ConfigurationChanged` deliberately avoids exactly this through its credential `Signature()` check (`GameLibraryArtwork.cs:285-312`). (2) It calls `OpenAsync` for the open app, which throws away the user's current tab, page, filter results, game search results and selected candidates, and reloads from the default tab. (3) That `OpenAsync` runs on the Avalonia dispatcher: `ArtworkStateStore.FindGame/ReadFilters` file reads and `Managed()`, which base64-reads up to five custom-art files of up to 16 MiB each under `_gate`.
- Recommendation: reuse the existing signature rule. Compare the artwork section (credentials plus tab visibility and order) with the last one seen. Reset caches and reopen only when it changed, and reset once from the parent. Move the reopen off the dispatcher. Belongs in LIBRARY-B3.

### LIBRARY-V-003 (low) The Manage tab misreports which icons are custom
- `Core/Artwork/SteamArtwork.cs:35` (`GridExtensions` = png, jpg, jpeg, webp), `:266-271`, `:362`, `:380-387`.
- (a) `ApplyIconAsync` writes a shortcut icon as `{appId}_icon.ico` when the bytes are ICO, but `FindCustomArtFile` never looks for `.ico`. The slot then shows as not custom, or shows an older `_icon.png` as current. (b) A shortcut icon reset only calls `SetShortcutIcon(id,'')` (toolkit `SteamApps.cs:508-514`) and leaves the `_icon.*` file, so the slot still reads as custom after a reset. (c) For a store title, any `appcache/librarycache/{id}_icon.jpg` counts as custom, but Steam's own cache keeps that file. `DataUrl`'s `.ico` MIME branch (`SteamArtworkBrowserSource.cs:1181`) is unreachable as a result.
- Recommendation: one slot-to-file rule shared by apply, clear and find (ico included). A shortcut reset deletes the file WSGM wrote. The store-title answer needs attended evidence of how Steam's cache looks before anything changes (same footing as LIBRARY-034).

### LIBRARY-V-004 (low, plausible) Store catalog images are filtered by URL suffix, against the "bytes decide" rule
- `Core/Library/StoreCatalogClient.cs:328-335`, pinned by `StoreCatalogClientTests.AnImageWithNoFormatTheApplyPathKnowsIsNotOffered` (`:128-139`).
- The comment says the apply path names the file by its suffix. That has not been true since `SteamArtwork.ImageFormat` began reading the format from the bytes (`SteamArtwork.cs:188-214`; Core CLAUDE.md: "an image's format is read from its first bytes, never its URL"). Display-catalog image URIs are commonly extensionless `store-images.s-microsoft.com/image/apps.<ids>` paths. If they are, every Xbox title loses its Store artwork.
- Recommendation: confirm with one real catalog answer or a log line first. If confirmed, drop the suffix filter (keep HTTPS-only) and invert the test. Same batch as LIBRARY-016.

### LIBRARY-V-005 (low) An unreachable add is reported as "nothing was created"
- `Shell/ShellSession.GameLibrary.cs:103-104`. `AddShortcutAsync` sends `CancellationToken.None` after dispatch, and an eval that times out comes back `Reachable=false`. The shortcut may exist. Recovery works (the next scan offers `Adopt` through `Unclaimed`), but the message is false and the stop reason misleads remote diagnosis from wsgm.log.
- Recommendation: word it "may not have been created; scan again before retrying". Map it in B5 to `DispatchedUnknown`, with no retry and no record because there is no AppId.

### LIBRARY-V-006 (nit) `TryReadIdAnd` ignores its `maximum` parameter
- `Shell/SteamLibraryImportSurface.cs:142-150`. Callers pass 32 or 8, and nothing enforces them. Delete the parameter. Do not reinstate the caps, per the no-arbitrary-limits rule. Type checks stay.

### LIBRARY-V-007 (nit) `AddFolderAsync` resolves a relative path against the process working directory
- `Shell/GameLibraryService.cs:680-689`. `Path.GetFullPath("Games")` produces an absolute path under WSGM's current directory, which then passes `IsPathFullyQualified`. Check `Path.IsPathFullyQualified(path)` on the input before normalizing. The pickers always send absolute paths, so this guards only a malformed page payload.

## Batch problems

1. **LIBRARY-B1 step 8 (`HasMore`) belongs in Core/Artwork.** Taking the provider's own page count changes the provider return shape (`IArtworkProvider`/`ArtworkSearchResult`), which LIBRARY-B2 rewrites. B2 declares no dependency on B1. Move step 8 into B2 or B3 so the provider seam changes once.
2. **LIBRARY-B1 step 2 cannot land on a default answer to Q1.** It changes what the review page shows (a new non-selectable "already imported from X" row). That is a UI and workflow change, which needs the maintainer's answer first. It must also include LIBRARY-V-001's Revalidate fix; otherwise the claimed-set rule is still bypassed on apply.
3. **LIBRARY-B1 step 9 should be replaced** by the one re-read after an unconfirmed update (corrected LIBRARY-004). Loosening `OwnsRecorded` blurs the exact-ownership rule the whole import design rests on (`ImportStateStore.cs:63-66`).
4. **LIBRARY-B1 step 3 (`ImportedEntry` → record) is not a correctness fix** (LIBRARY-007 downgraded). A record also changes `Equals` to value semantics on a type held in dictionaries and lists. Move it to B4b, where the apply code moves anyway, or drop it.
5. **LIBRARY-B4b "persist choices after releasing `_gate`" introduces a lost-update race.** Two edits to one title from the two surfaces (overlay on the UI thread, bridge on a pool thread) could reach `SaveChoice` in the opposite order to the edits, so the file keeps the older choice. The store's own lock orders the writes, not the edits. Keep the persist under `_gate`, so edit order is write order, and take the overlay's disk IO off the UI thread instead: make `ServiceSubView.Run` start the backend call on a worker. That fixes the LIBRARY-006 symptom without a new ordering mechanism.
6. **LIBRARY-B3 adds a tracked task set and `DisposeAsync(CancellationToken)` for the artwork browser** without a defect that needs joining. Its tasks only publish page state. The concrete defect (LIBRARY-012: `ObjectDisposedException` from `_shutdown.Token` after `Dispose`) goes away by cancelling without disposing the CTS, or by checking the disposed flag at each entry. That removes mechanism. B3 should also carry LIBRARY-V-002 and LIBRARY-V-003.
7. **LIBRARY-B6 edits `Core/PackagedLaunchCommand.cs`, which is compiled into `WSGM.PackagedLaunch` as a linked file** (`WSGM.PackagedLaunch.csproj:26`). The 2048-character change (LIBRARY-032) must change the launcher's own parse check at `:652` together with the compose and refusal checks at `:192, :397`, and the batch has to build the launcher project too. The `LibraryDisk` rewrite of nine source constructors (LIBRARY-029) is roughly 1,200 lines of seam churn with no defect behind it. Under "simplify" it is optional, and it must not run before the B0 golden tests.
8. **LIBRARY-B2 (about 1,300 lines) converts every artwork static to instances to gain test seams.** The only user-visible items in it are LIBRARY-015 (now a nit) and LIBRARY-016. Consider the smaller version: provider classes keep their shape, the `HttpMessageHandler` and the `ArtworkRequestGate` become constructor arguments with today's values as defaults, and the static `SteamGridDb` adapter folds into `SteamGridDbProvider`.
9. **The test filter (section 5) misses tests that cover touched code.** `ForegroundApplicationFilterTests` covers the projection LIBRARY-001 changes. `SteamCustomLaunchCommandTests` covers the quoting LIBRARY-030 pins. B4a/B4b claim the UI is unchanged, so they also need the `WSGM.UiTests` Game Library overlay captures, run per the root validation policy.
10. **The order is fine otherwise.** B0 → B1 → (B2 → B3) and (B4a → B4b) → B5 after toolkit I01 → B6 → B7 after the config domain. B1's `ConfigStore.cs` line (LIBRARY-017) needs the config domain's agreement, as the reviewer notes.
